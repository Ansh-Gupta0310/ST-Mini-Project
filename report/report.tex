\begin{abstract}
\noindent
We built a three-agent pipeline that generates a Python function for a programming task, generates unit tests
for that function, and executes those tests to produce a verdict. The test generator satisfies requirement~(1)
of the project statement: it targets a coverage criterion chosen by the user at run time. All three criteria
named in the statement are implemented, namely statement coverage, decision (branch) coverage and loop
coverage. On a fixed subset of 12 MBPP problems, the dataset's own tests cover 94.2\% of statements and 89.6\%
of branches of the generated code, while the generated tests reach 100\% of both. Because coverage alone does
not show that a test checks the right answer, every generated test is also run against an independent
reference implementation and labelled. That step shows that 69.3\% to 80.0\% of the generated tests are
correct, depending on the criterion, and that the tests detected a genuine fault in all three problems whose
generated code was wrong.
\end{abstract}

\section{Introduction}

Unit testing validates individual functions. Writing those tests by hand is slow, and a human stops at the
cases that come to mind. This project asks a narrower and measurable question: if a language model is asked to
write unit tests \emph{with an explicit coverage goal}, does it produce better tests than the ones shipped with
the benchmark?

To answer it we built an agentic pipeline of three agents, described in Section~\ref{sec:pipeline}. Two of the
agents call a language model; the third does not, because a verdict has to be a measured fact rather than a
model's opinion. The pipeline is written from first principles in plain Python, with no agent framework, no
retrieval and no chain-of-thought prompting (Section~\ref{sec:constraints}).

The project statement offers three alternative requirements for the test generator. We chose
requirement~(1), test cases that achieve a user-specified coverage criterion. The statement gives three
examples of such criteria, ``cover all statements, cover all loops, cover all decision statements'', and the
pipeline implements all three as command-line options.

Two results are worth stating at the outset. First, the generated tests reach a strictly higher coverage than
the dataset's own tests on every problem where the dataset falls short. Second, high coverage is not the same
as a good test suite: up to 31\% of the generated tests encode a wrong expected value or agree with a bug in
the code under test, which we measure rather than assume.

Two design points deserve emphasis.

\textbf{The Test Executor uses no language model.} It runs the tests in a separate process under
\texttt{coverage.py}, reads the JUnit XML report and the coverage JSON report, and applies fixed rules. If a
model were asked whether the tests covered every branch, the answer would be an unverifiable claim. Every
number in Section~\ref{sec:results} is instead a measurement that anyone can reproduce from the committed run
folders.

\textbf{Step [5] exists because of step [3].} The Test Generator is shown the code under test, which is
necessary for coverage (a test cannot target a branch that it cannot see) but dangerous for correctness. If the
code is wrong, a model that reads expected values off the code will write a test that agrees with the bug. The
generated tests are therefore re-run against an implementation the generator never saw.

\subsection{Dataset and problem selection}

We use MBPP (Mostly Basic Python Problems) in its sanitized form, which contains 427 hand-checked problems.
Each problem provides a short English description, a reference solution, and three assertions that act as the
dataset's own test suite. For example, problem 11 provides:

\begin{lstlisting}[style=plain]
assert remove_Occ("hello","l") == "heo"
assert remove_Occ("abcda","a") == "bcd"
assert remove_Occ("PHP","P") == "H"
\end{lstlisting}

The script \texttt{data/prepare\_dataset.py} selects a fixed subset deterministically, so that anyone who runs
it obtains the same problems. A problem is kept if it satisfies all five rules below, and the first 12 problems
in \texttt{task\_id} order that satisfy them are used.

\begin{enumerate}\itemsep2pt
  \item Its \texttt{task\_id} lies in MBPP's official test split, 11--510.
  \item Its reference solution contains at least two decision points, counted with Python's \texttt{ast}
        module (\texttt{if}, \texttt{for}, \texttt{while}, conditional expressions, \texttt{try}, and
        \texttt{if} clauses inside comprehensions).
  \item Its reference solution is at most 25 lines long.
  \item The function called in its first assertion is a top-level function of the reference solution, so that
        \texttt{from solution import f} works and the required signature can be extracted.
  \item Its reference solution passes its own three assertions. A broken reference would make every
        validation label in Section~\ref{sec:validity} meaningless.
\end{enumerate}

Rule 2 is the important one. Of the 257 problems in the test split, 113 contain no decision at all, so a single
test already gives 100\% coverage and there is nothing to measure. Table~\ref{tab:funnel} shows the effect of
the rules.

\subsection{Functionality of the test-case generator}

The requirement the generator satisfies is a coverage criterion chosen by the user, together with a target
percentage. Both are command-line arguments rather than constants:

\begin{lstlisting}[style=plain]
python pipeline.py --mode full --criterion branch    --target 100 --max-rounds 3 --out <folder>
python pipeline.py --mode full --criterion loops     --target 100 --max-rounds 3 --out <folder>
python pipeline.py --mode full --criterion statement --target 90  --max-rounds 1 --out <folder>
\end{lstlisting}

\paragraph{The three criteria.} Table~\ref{tab:criteria} defines them. In the standard terminology of
structural testing, statement coverage is node coverage and branch coverage is edge coverage, so the three
criteria are the bottom three levels of the standard subsumption hierarchy: prime path coverage subsumes
edge-pair coverage, which subsumes edge coverage, which in turn subsumes node coverage.

\begin{table}[htbp]
\centering
\small
\caption{The three user-selectable coverage criteria.}
\label{tab:criteria}
\begin{tabular}{@{}p{1.7cm}p{8.6cm}p{2.6cm}@{}}
\toprule
\textbf{\texttt{--criterion}} & \textbf{What the test suite must achieve} & \textbf{Standard name} \\
\midrule
\texttt{statement} & every executable line of \texttt{solution.py} is run by at least one test & node coverage \\
\texttt{branch} & every \texttt{if}, \texttt{elif} or \texttt{while} condition is True in some test and False
in some test; every loop runs its body and also finishes & edge coverage \\
\texttt{loops} & every pair of consecutive control-flow edges $a \rightarrow b \rightarrow c$. At a loop
header this requires a test that skips the body, a test that runs one iteration, and a test that runs two or
more & edge-pair coverage \\
\bottomrule
\end{tabular}
\end{table}

\paragraph{How coverage is measured.} Statement and branch coverage come straight from
\texttt{coverage.py}. It watches the program as it runs and then reports, for \texttt{solution.py} alone, how
many statements exist and how many of them ran, how many branches exist and how many were taken, and exactly
which lines and branches were missed. The pipeline reads the two percentages separately. It never uses the
combined figure that \texttt{coverage.py} also offers, because that one blends statements and branches together
and matches no criterion a user can ask for.

Loop coverage needs one thing that \texttt{coverage.py} does not provide, namely the \emph{order} in which the
lines ran. \texttt{coverage.py} reports the set of branches that were taken, not the sequence. The pipeline
therefore measures the two halves of the criterion separately (\texttt{agents/path\_coverage.py}):

\begin{enumerate}\itemsep3pt
  \item \textbf{What has to be covered} comes from \texttt{coverage.py}'s own parser, which lists every
        control-flow edge the function could possibly take, including the edges that jump back to a loop
        header. Each pair of consecutive edges in that list is one test requirement. Reusing the parser is a
        deliberate choice: the control-flow graph is then produced by the same established tool that measures
        the other two criteria, instead of by analysis code of our own that nobody has validated.
  \item \textbf{What was actually covered} comes from running the test suite a second time, during which a
        small tracer records the sequence of line numbers that each test executes. Every three consecutive
        line numbers in such a sequence form one covered pair.
\end{enumerate}

The second run cannot be folded into the first one. Python allows only a single active trace hook, so
\texttt{coverage.py} and our tracer would displace each other. We confirmed this experimentally: with the
tracer active inside \texttt{coverage run}, \texttt{coverage.py} reported 16.7\% statement coverage and 0\%
branch coverage instead of the true values. The traced run therefore executes without \texttt{coverage.py}, and
only when \texttt{--criterion loops} is requested, so the other two criteria are measured exactly as before.

One further detail matters for correctness. The tracer keeps a separate sequence for every \emph{call} of the
function rather than one sequence per test. In a recursive function a single combined sequence would mix the
inner call's lines into the outer call's, and a pair that really was executed would then appear untested.


\paragraph{The coverage feedback loop.} The generated suite is executed, and if the goal is not met and rounds
remain, the measured gap is turned into plain sentences and sent back with the tests written so far:

\begin{lstlisting}[style=plain]
Coverage after running them: statements 80%, branches 75%.
Not covered yet:
- line 4 `return False` was never run
- line 3 `if len(s) < 3:` never went to line 4 `return False`
\end{lstlisting}

The model is asked for new tests only. The new file is joined to the existing one using \texttt{ast}: every
import once, then the earlier tests, then the new ones, with a duplicate test name renamed to
\texttt{<name>\_r<round>} so that no earlier test is silently replaced. Each round is executed in its own
folder, so the single-shot result (round 1) and the result with feedback are both available from one run.
Passing \texttt{--max-rounds 1} switches the loop off.

This loop is ordinary control flow: a program passes a measurement from one tool back into the next prompt. It
is not chain-of-thought prompting, as discussed in Section~\ref{sec:constraints}.

\paragraph{Checking the generated file.} A reply is used only if it contains a Python code block that parses,
defines at least one top-level function whose name begins with \texttt{test\_}, imports the module
\texttt{solution}, does not define the function under test (which would mean testing its own copy), and does
not import anything that breaks determinism or the ``no files, no network'' rule. A reply that fails any of
these checks is discarded and the round counts as unusable.

\paragraph{Validation of the tests.} After the loop, the final suite is run once more against MBPP's reference
solution, which the Test Generator never saw, and each test is labelled from the two outcomes
(Table~\ref{tab:labels}). Coverage says how much of the code the tests reach; these labels say whether the
tests are right.

\begin{table}[htbp]
\centering
\small
\caption{Test labels, assigned by comparing two executions of the same test.}
\label{tab:labels}
\begin{tabular}{@{}llll@{}}
\toprule
\textbf{On the generated code} & \textbf{On MBPP's reference} & \textbf{Label} & \textbf{Meaning} \\
\midrule
pass & pass & \texttt{VALID} & correct test \\
fail & pass & \texttt{BUG\_FOUND} & the test caught a real fault in the generated code \\
fail & fail & \texttt{INVALID\_TEST} & the test's expected value is wrong \\
pass & fail & \texttt{MISLEADING} & test and code share the same wrong behaviour \\
\bottomrule
\end{tabular}
\end{table}

\section{Prompts and settings}

\subsection{Code Generator prompts}

The system prompt (\texttt{prompts/code\_generator\_system.txt}) is sent unchanged:

\begin{lstlisting}[style=plain]
You are a Python code generator.
Write a correct Python 3 function that solves the problem you are given.
Reply with exactly one Python code block and nothing else.
Use only the Python standard library.
Do not include explanations, example usage, print statements, input() calls,
or an `if __name__ == "__main__":` block.
\end{lstlisting}

The user prompt is a template filled by the pipeline with Python's \texttt{string.Template}, so that braces in
code cannot break the substitution:

\begin{lstlisting}[style=plain]
Problem:
$prompt

Implement this function, keeping exactly this name and these parameters:
$signature

Your function must satisfy this example:
$example_test
\end{lstlisting}

The prompt that was actually sent for problem 11, taken from the committed log
\texttt{results/phase1\_baseline/Mbpp\_11/llm\_calls.jsonl}:

\begin{lstlisting}[style=plain]
Problem:
Write a python function to remove first and last occurrence of a given character from the string.

Implement this function, keeping exactly this name and these parameters:
def remove_Occ(s, ch):

Your function must satisfy this example:
assert remove_Occ("hello","l") == "heo"
\end{lstlisting}

Only the first of the three MBPP assertions is shown, because its purpose is to fix the input and output
format (for instance, whether the function returns \texttt{True} or the string \texttt{"Yes"}). The model never
sees the reference solution. All three assertions are used afterwards, by the Test Executor, to decide whether
the generated code is correct.

\subsection{Test Generator prompts}

The system prompt (\texttt{prompts/test\_generator\_system.txt}), where \texttt{\$entry\_point} is the name of
the function under test:

\begin{lstlisting}[style=plain]
You are a software tester who writes pytest unit tests.
Reply with exactly one Python code block containing a complete pytest file and nothing else.
Rules:
- The function under test is in the module `solution`. Import it with: from solution import $entry_point
- Write each test as a separate top-level function whose name starts with test_ and describes what it checks.
- Use plain assert statements. Use pytest.raises only if the problem says an exception is raised.
- Take every expected value from the problem description, not from the code under test.
- Do not define or change $entry_point. Do not use randomness, files, the network, or print.
- Use only pytest and the Python standard library.
\end{lstlisting}

The instruction to take expected values from the description rather than from the code is the pipeline's first
defence against the oracle problem. Section~\ref{sec:validity} measures how well it worked.

The first-round user prompt (\texttt{prompts/test\_generator\_user.txt}):

\begin{lstlisting}[style=plain]
Problem description:
$prompt

Example of correct behaviour:
$example_test

Function under test (file solution.py; the line numbers on the left are not part of the code):
$numbered_code

Coverage goal: $criterion_goal
Write between 3 and 10 tests.
\end{lstlisting}

The feedback-round user prompt (\texttt{prompts/test\_generator\_feedback.txt}):

\begin{lstlisting}[style=plain]

\section{Formats of the code, the tests and the verdict}

\subsection{Generated code}

\texttt{solution.py} contains the required function with the exact signature taken from the dataset. Helper
functions and standard-library imports are allowed. The reply is post-processed deterministically: the first
Python code block is extracted, it must parse and must define the required function at top level, and
top-level example code is removed (an \texttt{if \_\_name\_\_ == "\_\_main\_\_":} block, bare calls such as
\texttt{print(...)}, and top-level assertions). Such lines are not part of the unit, no test could ever cover
them, and they would run on import. If no usable code can be extracted, the problem is recorded as
\texttt{CODEGEN\_FAILED}. This did not occur: all 12 problems produced usable code.

\subsection{Generated test files}

The required shape of \texttt{test\_solution.py} is shown below. The rules listed in
Section~\ref{sec:pipeline} are enforced by the pipeline rather than assumed.

\begin{lstlisting}[style=py]
from solution import remove_Occ


def test_removes_first_and_last_occurrence():
    assert remove_Occ("hello", "l") == "heo"


def test_character_not_present_returns_the_same_string():
    assert remove_Occ("abc", "z") == "abc"
\end{lstlisting}

MBPP's own three assertions are wrapped in the same format so that the baseline and the generated suite are
executed by identical machinery. The file produced for problem 92 is:

\begin{lstlisting}[style=py]
from solution import *


def test_reference_1():
    assert is_undulating(1212121) == True

def test_reference_2():
    assert is_undulating(1991) == False

def test_reference_3():
    assert is_undulating(121) == True
\end{lstlisting}

\subsection{Verdicts and test labels}

The Test Executor runs the command below in a throw-away folder, with a 30 second timeout and with the API key
removed from the environment:

\begin{lstlisting}[style=plain]
python -m coverage run --branch --include=solution.py -m pytest -q --junitxml=junit.xml test_solution.py
python -m coverage json -q -o coverage.json
\end{lstlisting}

It then reads the per-test outcome from \texttt{junit.xml} and the coverage numbers from
\texttt{coverage.json}, and applies the rules in Table~\ref{tab:verdicts} in order.

\begin{table}[htbp]
\centering
\small
\caption{Verdict rules, checked in this order.}
\label{tab:verdicts}
\begin{tabular}{@{}ll@{}}
\toprule
\textbf{Verdict} & \textbf{Condition} \\
\midrule
\texttt{ERROR} & the file could not be run: syntax or import error, no tests collected, or a timeout \\
\texttt{TESTS\_FAILED} & at least one test failed \\
\texttt{COVERAGE\_NOT\_MET} & all tests passed, but coverage is below the target \\
\texttt{PASS} & all tests passed and coverage is at or above the target \\
\bottomrule
\end{tabular}
\end{table}

Whether the target is met depends on the criterion: \texttt{statement} requires statement coverage at or above
the target; \texttt{branch} requires branch coverage \emph{and} statement coverage; \texttt{loops} requires
edge-pair, branch and statement coverage. Each criterion also demands the weaker ones it subsumes, for a
measurement reason rather than a pedantic one. A function with no decisions has no branches and no edge pairs,
and zero out of zero is reported as 100\%, so either criterion on its own would pass code that no test ever
calls. Four of the 12 generated solutions contain no decision, which is why this guard matters in practice.

Note also that test failures and coverage are reported side by side and never merged, because coverage counts
lines run even by a test whose assertion fails. A suite can therefore reach 100\% coverage and still have a
verdict of \texttt{TESTS\_FAILED}, which is exactly what happens when the tests catch a fault.

\subsection{Worked example 1: problem 92, the coverage gap closed}

The generated solution for problem 92 (\texttt{results/phase2\_branch100/Mbpp\_92/solution.py}):

\begin{lstlisting}[style=py]
def is_undulating(n):
    s = str(n)
    if len(s) < 3:
        return False
    if len(set(s)) != 2:
        return False
    for i in range(len(s) - 2):
        if s[i] == s[i+1] or s[i+1] == s[i+2]:
            return False
    return True
\end{lstlisting}

The three MBPP assertions all pass, so the code is correct, but they leave lines 4 and 6 unexecuted and the
decisions on lines 3 and 5 never come out False. None of them uses a number with fewer than three digits or
with more than two distinct digits. The executor records this as:

\begin{lstlisting}[style=plain]
"tests_total": 3, "tests_passed": 3,

\subsection{Worked example 2: problem 71, a fault detected}

\begin{lstlisting}[style=py]
def comb_sort(nums):
    n = len(nums)
    gap = n
    shrink = 1.3
    sorted_flag = False

    while not sorted_flag:
        sorted_flag = True
        gap = max(1, int(gap / shrink))
        for i in range(n - gap):
            if nums[i] > nums[i + gap]:
                nums[i], nums[i + gap] = nums[i + gap], nums[i]
                sorted_flag = False
    return nums
\end{lstlisting}

The loop stops as soon as one pass makes no swap, even while the gap is still greater than one, so the list can
be left unsorted. This example is instructive because the dataset's own assertions already reach 100\%
statement and 100\% branch coverage on this function, and the function is still wrong. Coverage is not
correctness.

Of the seven generated tests, four pass and three fail. Validation labels all three failures
\texttt{BUG\_FOUND}, because they pass on MBPP's reference solution:

\begin{lstlisting}[style=py]
def test_comb_sort_reverse_sorted():
    assert comb_sort([5, 4, 3, 2, 1]) == [1, 2, 3, 4, 5]          # BUG_FOUND

def test_comb_sort_gap_reduction_true():
    result = comb_sort([5, 15, 37, 25, 79])
    assert result == [5, 15, 25, 37, 79]                           # BUG_FOUND

def test_comb_sort_sorted_flag_false():
    result = comb_sort([10, 3, 7, 1, 9])
    assert result == [1, 3, 7, 9, 10]                              # BUG_FOUND
\end{lstlisting}

The same effect is clearer still for problem 79. Its description asks whether the length of a word is odd, and
the generated code returns \texttt{len(s) \% 2 == 0}. Because the generator was told to take expected values
from the description, it wrote the tests for ``odd'', and four of its six tests are labelled
\texttt{BUG\_FOUND}. Had it read the expected values off the code, all six would have passed and the pipeline
would have reported a clean result for broken code.

\subsection{Results of the Code Generator and of the baseline}

The Code Generator produced usable code for all 12 problems. Nine of the 12 solutions pass all three MBPP
assertions, a correctness rate of 75\%. The three failures are findings rather than defects of the pipeline:

\begin{itemize}\itemsep2pt
  \item \textbf{71 \texttt{comb\_sort}}: a genuine algorithmic fault, described above.
  \item \textbf{79 \texttt{word\_len}}: an inverted condition. The description asks whether the length is odd
        and the code tests for even, contradicting even the example it was given.
  \item \textbf{83 \texttt{get\_Char}}: an ambiguous specification. The text says ``adding the ASCII value of
        all the characters \ldots{} modulo 26'', while the expected answers use alphabet positions. The model
        followed the text. MBPP's own reference also returns the integer \texttt{122} instead of \texttt{"z"}
        when the sum is a multiple of 26.
\end{itemize}

Run against those 12 solutions, MBPP's own tests cover 94.2\% of statements and 89.6\% of branches on average,
and reach the 100\% branch coverage goal for only 7 of the 12 problems. Five correct solutions (11, 20, 69, 70
and 92) contain branches that the dataset's tests never execute. That is the gap the generated tests are meant
to close.

Three observations follow.

\textbf{Every criterion improves on the dataset's tests.} This is the result the project set out to measure.

\textbf{The criterion changes the suite but not the coverage reached.} Asking for statement coverage produced
80 tests, branch coverage 88 and loop coverage 140, and the test sets differ problem by problem. Yet all three
suites end at the same coverage, namely 100\% of statements, 100\% of branches and 97.1\% of edge pairs. On

it, so the stronger criteria have little left to ask for. Larger functions would be needed to separate them.

\textbf{Only the \texttt{loops} criterion reveals that 97.1\% is a ceiling.} Under \texttt{statement} and

orderings that no input can execute. Under \texttt{loops} those four are reported as
\texttt{COVERAGE\_NOT\_MET} with the unmet requirement named in \texttt{verdict.json}. Stated the other way
round, all three criteria satisfied every requirement that was reachable; the remaining 2.9\% consists entirely
of infeasible requirements.

The \texttt{loops} criterion is also the only one for which the feedback loop had work to do, since round 1 did
not already meet its goal. It used 1.67 rounds on average. It could not raise coverage, because what was
missing was infeasible, but it kept adding usable tests: problem 92 grew from 7 tests in round 1 to 25 after
round 3, and all 25 are labelled \texttt{VALID}.

\subsection{Infeasible test requirements}

Each of the four shortfalls under the \texttt{loops} criterion is a requirement that no input can satisfy, and
all four have the same shape: a loop whose body cannot be skipped, because a guard above it has already
established that the loop has work to do. Problem 70 is representative.

\begin{lstlisting}[style=py]
def get_equal(Input):
    if not Input:
        return True            # an empty Input returns here
    first_len = len(Input[0])
    for tup in Input:          # so by this line, Input is non-empty
        if len(tup) != first_len:
            return False
    return True                # reaching this line directly from the loop header is impossible
\end{lstlisting}

The required pair $4 \rightarrow 5 \rightarrow 8$ asks for a test that reaches the loop, skips its body and
returns. Table~\ref{tab:infeasible} gives all four cases.

This is the classical infeasible-requirement problem of structural coverage: the stronger the criterion, the
more of its requirements no input can satisfy, and 100\% stops being a meaningful target. It also explains why
three rounds of feedback could not help these four problems. The pipeline handles the situation in the only
honest way available to it: the goal is not met after the final round, so the verdict is
\texttt{COVERAGE\_NOT\_MET} and the unmet requirement is recorded for a human to judge. We did not lower the
target in order to obtain a better-looking table.

\texttt{INVALID\_TEST} cases are arithmetic mistakes, for example
\texttt{len\_log(["Python", "pYTHON", "PYTHON"]) == 7} where every word has six characters. The nine
\texttt{MISLEADING} cases are the oracle problem itself: five of them (problems 11 and 92) are places where the
description does not pin the behaviour down, and the model, having been shown the code, resolved the ambiguity
the same way the code did. No coverage number reveals this. Only the second execution against an independent
implementation does.

Two caveats belong with these labels. They treat MBPP's reference as the oracle, so where the reference itself
is questionable (problem 92, as discussed above, or problem 83) a reasonable test is labelled
\texttt{MISLEADING} or \texttt{INVALID\_TEST}. And a label records disagreement between two implementations,
not a verdict on the test in isolation.

The \texttt{loops} criterion produced both the largest and the most valid suites, 140 tests at 80.0\% validity
with only five \texttt{MISLEADING}, where the branch criterion produced the least valid, 69.3\% with nine
\texttt{MISLEADING}. We cannot prove the cause from a single run, but the plausible explanation is that asking
for orderings pushes the model towards ordinary edge cases, such as an empty list or a value that fails on the
last iteration, whereas asking for branches pushed it towards contrived inputs chosen to flip a condition,
which is where it tended to read the expected value off the code.

\subsection{Cost and reproducibility}

The whole project sent \textbf{59 requests} to the API, one per distinct prompt, each stored in
\texttt{llm\_cache/}: one connectivity check, 12 code generations, 36 first-round test generations (12 problems
by three criteria) and 10 feedback-round test generations. Those requests consumed 24{,}168 prompt tokens and
15{,}491 completion tokens, and \textbf{0 reasoning tokens}. No fallback model was needed and no request had to
be retried.

Because the cache is keyed on the exact request body and is committed with the results, re-running any
experiment reproduces the same numbers at no API cost. The script \texttt{verify\_run.py} re-derives every
verdict in a finished run from the measurements it was computed from, and checks that every final test file
still satisfies the rules of Section~\ref{sec:pipeline}. The pipeline code itself is covered by 114 offline
tests, none of which contacts the API.

\section{Conclusions/Findings:}

\begin{itemize}\itemsep3pt
  \item \textbf{The feedback loop could not be shown to improve coverage.} Round 1 already met the goal for
        every problem under \texttt{statement} and \texttt{branch}. Under \texttt{loops} the loop did run, but
        every problem it ran for was short by an infeasible requirement, so the extra rounds added tests
        without adding coverage.
  \item \textbf{Infeasible requirements make a 100\% target unsuitable for the \texttt{loops} criterion} on
        this benchmark, as four of the twelve problems show.
  \item \textbf{Prime path coverage is not implemented.} It would require path enumeration on top of the
        control-flow graph and a policy for sidetrips around infeasible paths. Unlike the other three criteria
        it could not be reduced to a measurement taken from an established tool.
\end{itemize}
